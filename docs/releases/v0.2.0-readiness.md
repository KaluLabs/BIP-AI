# v0.2.0 release readiness

This document records the evidence expected before the `v0.2.0` tag is created.

## Product scope

BIP-009 through BIP-016 are complete. The v0.2.0 release candidate contains the daily-use editorial workspace, automated capture, review/publishing operations, first-run onboarding, and reproducible distribution paths.

## Persistent-state compatibility

The release candidate includes `test/migration-v010.test.js`.

That test constructs the exact persistent schema shipped by tag `v0.1.0`, inserts representative event/campaign/campaign-version records, then opens the database with the v0.2 `BipStore`.

It verifies that:

- v0.1 event data is preserved;
- v0.1 campaign data is preserved;
- v0.1 campaign-version history is preserved;
- v0.2 `publishing_journal` and `capture_sources` tables are added;
- append-only publishing-journal triggers are added;
- new capture state can be written after upgrade;
- new publishing-journal state can be appended after upgrade.

The current v0.2 schema adds new structures with `CREATE ... IF NOT EXISTS`; it does not destructively rewrite the original v0.1 tables.

## Security/privacy fail-closed evidence

The automated suite covers the release invariants, including:

- privacy `BLOCK` prevents draft generation;
- privacy `REVIEW` remains human-gated;
- unsupported provider output falls back or remains held for review;
- campaign approval is bound to exact `version + contentHash`;
- edits invalidate prior approval/handoff state;
- scheduled publishing refuses missing/stale approval;
- PAG denial/failure does not bypass the handoff boundary;
- safe retry refuses changed content and terminal denial;
- publishing history remains platform-isolated;
- diagnostics redact configured token/API-key values.

`SECURITY.md` remains the normative trust-boundary policy.

## Repository/release exposure evidence

`npm run audit:release` verifies the current release tree:

- no tracked local/private state such as `.env`, `.bipai`, SQLite/WAL, `node_modules`, or generated `dist`;
- no tracked private-key/certificate-key filenames;
- no high-confidence credential-shaped values for the supported scan families;
- secret-bearing `.env.example` entries are blank;
- package-registry publication remains disabled with `private: true`.

The Docker distribution test separately verifies that local `.env` and `.bipai` state are not copied into the image.

## Distribution/reproducibility evidence

`npm run verify:distribution` verifies:

- deterministic source-archive SHA-256 generation for the same commit/version;
- clean extracted-source setup/doctor/version operation;
- Docker image build;
- packaged runtime version identity;
- container health/readiness;
- persistent state across container replacement;
- persistent state across replacement-image build;
- npm publication guard.

## Final tag gate

Do **not** create `v0.2.0` until:

1. the release-candidate PR CI is green;
2. the release candidate is merged through protected `main`;
3. the post-merge `main` CI is green on the exact release commit;
4. the source artifact/checksum is generated from that verified commit;
5. the artifact manifest/checksum is reviewed.

The GitHub release and tag are a separate final publication action after these gates pass.
