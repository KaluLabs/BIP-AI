# BIP-AI v0.2.0

> Release notes prepared for the v0.2.0 productization release. Tagging and GitHub release publication happen only after the release checklist is complete.

BIP-AI v0.2.0 turns the v0.1 foundation into a daily-use operating surface for capture, review, scheduling, safe publishing handoff, onboarding, and reproducible installation.

## Highlights

### Editorial workspace

- per-platform X/LinkedIn scheduling
- timezone-aware planned publication
- Control Room search, filters, sorting, pagination, and URL-backed navigation
- explicit drafted / approved / planned / handed-off / published / failed lifecycle state

### Automated capture

- restart-safe local Git capture scheduler
- durable cursors and bounded retry backoff
- optional GitHub activity capture for commits, pull requests, issues, releases, and CI milestones
- capture health and manual-run controls

### Review and publishing operations

- operational approval inbox
- privacy REVIEW resolution with required rationale
- stale-approval detection
- append-only publishing/PAG journal
- receipt reconciliation after restart
- exact version/content-hash safe retries
- terminal PAG denial and platform-isolated retry behavior

### First-run onboarding

- restartable `setup` workflow
- interactive and non-interactive project registration
- local-state initialization
- `doctor` diagnostics
- deterministic drafting as the zero-key default
- read-only PAG health checks
- redacted provider/PAG/token diagnostics

### Distribution

The supported v0.2 installation methods are:

1. **checksummed source archive** generated from the exact release commit;
2. **Docker/Compose packaged runtime** with persistent `/data` state.

BIP-AI remains `private: true` in `package.json` and is **not published to npm**.

Release artifacts should include:

```text
bip-ai-v0.2.0.tar.gz
SHA256SUMS.txt
release-manifest.json
```

Verify the archive before use:

```bash
sha256sum -c SHA256SUMS.txt
tar -xzf bip-ai-v0.2.0.tar.gz
cd bip-ai-v0.2.0
node ./src/cli.js version
node ./src/cli.js setup my-project /path/to/project
node ./src/cli.js doctor
```

Docker users can build from the release checkout:

```bash
docker build \
  --build-arg BIP_AI_VERSION=0.2.0 \
  --build-arg BIP_AI_REVISION="$(git rev-parse HEAD)" \
  -t bip-ai:0.2.0 .
```

Keep `/data` on a named volume or persistent mount across container replacement and upgrades.

See [Distribution and installation](../DISTRIBUTION.md) for the complete source, Docker, Compose, persistence, secrets, health, and upgrade workflow.

## Runtime identity and health

A packaged installation reports its version through:

```bash
node ./src/cli.js version
```

and:

```text
GET /api/health
```

Docker images can additionally carry the release revision through `BIP_AI_REVISION`.

## Security and persistence

- secrets are supplied at runtime, never embedded in source archives or Docker build arguments;
- Docker build context excludes local `.env`, `.bipai`, SQLite files, Git history, and build output;
- the packaged runtime runs as a non-root user;
- Compose publishes the Control Room to host loopback only;
- persistent state lives outside the image under `/data`;
- PAG remains the external publishing authority.

## Upgrade notes

v0.2 schema changes are designed to be backward-compatible with v0.1 local SQLite state.

Before upgrading:

1. keep a backup/copy of the persistent BIP-AI state;
2. verify the release checksum;
3. retain the same `/data` volume or local `.bipai` state;
4. run `doctor` after upgrade;
5. verify `/api/health` before normal operation.

## Release verification

The release candidate must pass:

```bash
npm test
npm run verify:distribution
```

Distribution CI verifies reproducible source archives, clean setup, Docker build/health, persistent state across container restart/image replacement, version reporting, and the npm-publication guard.
